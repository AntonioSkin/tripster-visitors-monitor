# Контроль сроков задач

Внутренний контроль: `health/check.py` и workflow Monitoring deadlines.
Он проверяет данные и доставку, но зависит от планировщика GitHub.

Внешний контроль: `health/external.py` и Healthchecks.io. Четыре проверки
живут вне GitHub и подают тревогу, если подтверждение успеха перестало приходить.

| Задача | Ожидаемый запуск, Шымкент | Повторные попытки / срок тревоги |
|---|---|---|
| 1. Посетители | ежедневно с 08:00 | до 13:00 |
| 2. Места 0–6 | каждые 30 минут | без подтверждения 90 минут |
| 3. Юлия и Дмитрий | 11:00 и 20:00 | до 13:00 и 22:00 |
| 4. Wise RUB/KZT | 11:00 и 20:00 | до 13:00 и 22:00 |

## Однократное подключение

1. В настройках **проекта** Healthchecks создайте API key **Read-write**.
2. Сохраните его только в GitHub → Settings → Secrets and variables → Actions →
   New repository secret с именем `HEALTHCHECKS_API_KEY`.
3. Запустите workflow **Configure external Healthchecks** или повторите его job.
   Он создаст четыре проверки с постоянными slug, назначит уже подключённые
   Telegram и email, активирует сроки первого цикла и проверит результат.
   При успехе отправит подтверждение в обычный чат бота.

Без секрета внешний контроль **не активен**. Пароль аккаунта не нужен.
API key и ping URL не записываются в репозиторий, сообщения или журналы.
Ключ Read-write даёт GitHub доступ к проверкам и интеграциям только выбранного
проекта Healthchecks; это не ключ аккаунта целиком. Не используйте проект с
чужими или не относящимися к этому мониторингу проверками.

## Что подтверждает успех

Подтверждение отправляется после сохранения данных в GitHub отдельным заданием записи.
Сбор каждой задачи выполняется независимо, повторные запуски одной задачи — последовательно.
Запись всех задач проходит через короткую очередь `monitor-results-write` с `queue: max`.
Резервный процесс запускает исходные workflows через dispatch и использует те же блокировки.
Подробности отката: `workflow_support/README.md`.

Подтверждение отправляется после сохранения данных в GitHub. Задача 1 требует
все выбранные счётчики и отметку отправки; задача 2 — недавние успешные проверки
всех четырёх экскурсий; задача 3 — семь снимков текущего замера и общий отчёт;
задача 4 — текущий замер и завершённую обработку (включая случай без изменения курса).
Повторный запуск с теми же или старыми данными не обновляет Healthchecks.

Начальная настройка не подставляет фиктивный успешный замер. Для первого
незавершённого цикла используется start с временем до окончания повторных
попыток; если срок уже пропущен, отправляется fail. После настоящего успеха
восстанавливается обычный grace. В остальных случаях промежуточные ошибки
не отправляются как fail: повторы продолжаются до целевого срока.

Тревоги и восстановление доставляет **HealthchecksBot** в ранее подключённый
чат. Обычные отчёты остаются у VisitorsTripCompetitorsBot.
Для задачи 2 служебные сообщения об ошибках, пропусках срока и восстановлении
в основной чат не отправляются — их доставляет только HealthchecksBot.
Проверки, запись ошибок и уведомления об остатках 0–6 мест продолжаются.
Отправка сигнала тоже имеет повторы; workflow Monitoring deadlines дополнительно
пытается передать подтверждения свежих замеров. Недоступность самого
Healthchecks или Telegram остаётся внешней зависимостью.

Эта настройка контролирует сроки. Она не создаёт внешний автоматический
перезапуск GitHub по вебхуку. Существующие повторные попытки сбора сохраняются.

Документация: https://healthchecks.io/docs/api/ и https://healthchecks.io/docs/http_api/
