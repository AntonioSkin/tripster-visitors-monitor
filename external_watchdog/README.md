# Внешний контролёр семи задач Tripster

Целевой Worker: `tripster-external-watchdog`. Один независимый Cron Trigger раз в
10 минут и один SQLite Durable Object для журнала, блокировки и лимитов повторов.
Все часы задач рассчитаны для Шымкента (`Asia/Almaty`, UTC+5).

**Статус 08.11.2026: исходники подготовлены; в Cloudflare не развёрнут.** Вход
через Google в облачном браузере завершился сообщением `Something went wrong`.
Ручной вход в переданном браузере также не удался. Подготовлен альтернативный
запуск через GitHub Actions без сессии браузера. Создание Worker и реальные
события Cloudflare Cron пока не подтверждены.
Этот файл не означает, что внешний контроль уже работает.

## Наблюдение

`MODE=observe`, `RECOVERY_ALLOWLIST=""` — настройки по умолчанию. Наблюдение не
вызывает GitHub POST, не отправляет Telegram и не обращается к Healthchecks.
HTTP-интерфейс всегда возвращает 404; `workers.dev` и preview URLs выключены.
Результаты доступны в Cloudflare Logs и в последнем состоянии Durable Object.
Хранятся последние 100 проверок, без токенов, данных билетов и контактов клиентов.

| № | Workflow | Подтверждение результата |
|---|---|---|
| 1 | daily.yml | 10 числовых счётчиков и отметка отправки за текущую дату |
| 2 | seats.yml | успешные проверки всех четырёх экскурсий моложе 90 минут |
| 3 | calendar-history.yml | общий отчёт по семи экскурсиям для текущего интервала |
| 4 | fx.yml | текущий курс и завершённая обработка интервала |
| 5 | closures.yml | семь экскурсий, сохранённое завершение моложе 90 минут |
| 6 | tickets.yml | успешное завершение проверки билетов после 11:00 |
| 7 | monitor.yml в tripster-price-monitor | состояние выполнения; качество данных пока не подтверждается |

Для задач 1, 3, 4, 6 оставлены 45 минут для обычного планировщика и повторов.
Задачи 3 и 4 восстанавливаются только внутри исходного двухчасового окна.
Прошедшие интервалы фиксируются как пропуск; исторические данные не выдумываются.
Проверяется текущий ожидаемый интервал, а не полнота всех прошлых интервалов.

У задачи 7 сейчас нет общей очереди и достоверной отметки чтения всех цен.
Контролёр показывает `unverified`, даже если GitHub показывает `success`.
Её автоматический повтор заблокирован в коде. Для полноценного контроля нужны
проверка всех цен, надёжная отметка завершения и очередь `tripster-task-7` в её
исходном workflow. Существующий мониторинг цен здесь не изменён.

## Восстановление

После проверки наблюдения в Cloudflare восстановление включается отдельно:
`MODE=recover`, `RECOVERY_ALLOWLIST="1,2,3,4,5,6"`. Пока эти параметры не заданы,
контролёр остаётся в режиме чтения. Токен сам по себе не включает восстановление.

Перед каждой попыткой повторно читаются текущая main, данные, отметки доставки,
настройки очереди исходного workflow и все активные/ожидающие запуски. Ошибка
GitHub, неполный ответ, неизвестное состояние или отсутствие подтверждённой
очереди запрещают восстановление. Читается не более 48 GitHub API ответов за цикл.

Контролёр вызывает только исходные workflows через dispatch. Успешный сбор при
неуспешной записи восстанавливается повтором одного `save` job с исходным,
непросроченным artifact; успешный сбор и Telegram не запускаются повторно.
При неопределённой доставке или несохранённом состоянии требуется разбор вручную.
При частичной ошибке сбора новый запуск допускается только после успешной записи
состояния дедупликации. Принятый GitHub запрос ещё не считается восстановлением:
следующая проверка должна увидеть настоящие свежие данные.

Лимиты: одна попытка на проверку, пауза 45 минут, не более двух попыток одного
сбоя и не более 12 попыток за календарный день Шымкента. Попытка сохраняется до
POST. Таймаут или авария после этого запрещают её автоматическое повторение до
появления нормальных данных или ручного разбора. Одна атомарная аренда на 15 минут
и обычные очереди задач защищают от параллельных проверок.

Telegram не предоставляет идемпотентную отправку: сетевой сбой после фактической
доставки может оставить неопределённость. Контролёр удерживает такие случаи,
а не обещает абсолютное отсутствие дублей.

## Подключение к Cloudflare

### Развёртывание через GitHub Actions

В репозитории подготовлен `Deploy external watchdog (observation)`.
Ему нужны два repository secrets в `tripster-visitors-monitor`:

| Имя | Значение и область доступа |
|---|---|
| `CLOUDFLARE_API_TOKEN` | отдельный ключ для развёртывания Workers только выбранного Cloudflare account |
| `WATCHDOG_GITHUB_TOKEN` | новый fine-grained token: только два репозитория мониторинга, Contents read и Actions write |

Account ID определяется запросом GET к списку доступных аккаунтов Cloudflare.
Если доступен ровно один аккаунт, его ID используется в том же задании, без
публикации названия аккаунта и без дополнительного ручного копирования. Если
аккаунтов несколько или список неполон, развёртывание останавливается: тогда
нужно явно задать необязательный secret `CLOUDFLARE_ACCOUNT_ID`.

Cloudflare рекомендует шаблон Edit Cloudflare Workers, ограниченный нужным
аккаунтом. Права на DNS, зоны и другие неиспользуемые продукты добавлять не нужно.
Ключи создаются и сохраняются владельцем через официальные интерфейсы Cloudflare
и GitHub; их значения не передаются в чат. Не использовать Global API Key и
старый `GH_PAT` из мониторинга цен. После загрузки GitHub-ключ сохраняется как
зашифрованный secret Worker `GITHUB_TOKEN`; Cloudflare-ключ остаётся в GitHub CI.

Без секретов workflow только сообщит об ожидании настройки. Перед развёртыванием
он проверяет доступ к Cloudflare и двум репозиториям запросами GET, запускает тесты
и запрещает конфигурацию с включённым восстановлением или публичным endpoint.
После добавления секретов его можно запустить вручную, когда workflow попадёт в
main. Помощник также может инициировать запуск разрешённым изменением файлов
контролёра. Успешный deploy означает загрузку конфигурации; событие Cron и реальная
проверка восстановления подтверждаются отдельно.

### Развёртывание через панель Cloudflare

1. Войти в ранее зарегистрированный аккаунт Cloudflare, оставить Workers Free.
2. Загрузить проект из этой папки с конфигурацией `wrangler.toml`, включая
   миграцию SQLite Durable Object `WatchdogState`. Исходники хранятся в GitHub;
   интеграция Cloudflare Builds с доступом ко всем репозиториям не нужна.
3. Добавить `GITHUB_TOKEN` как зашифрованный secret Worker. Не добавлять его в
   обычные vars, исходники, логи или сообщения. Подключение GitHub к ChatGPT
   не передаёт Worker отдельные учётные данные автоматически.
4. Для наблюдения достаточно fine-grained GitHub token с `Actions: read` и
   `Contents: read` только для `tripster-visitors-monitor` и `tripster-price-monitor`.
   Для последующего восстановления нужен `Actions: write` и `Contents: read`
   для этих же двух репозиториев; права записи кода, Secrets и Administration не нужны.
   Разрешение Actions write технически шире dispatch; сам код использует только
   dispatch и повтор конкретного job. Установить срок действия и напоминание о замене.
5. Проверить фактическое событие Cron и структурированный отчёт по семи задачам.
   Новое расписание может распространяться до 15 минут. Наблюдение без токена
   возможно для публичных данных, но общего анонимного лимита GitHub недостаточно
   для стабильной работы с этой частотой.
6. Сначала провести изолированную проверку восстановления, затем включать
   `recover` только для проверенных задач. Публиковать endpoint для запуска не нужно.

Worker и SQLite Durable Object доступны на Free. При превышении бесплатных
лимитов Cloudflare возвращает ошибки. Этот проект не оформляет платный план,
не добавляет карту и не создаёт платные ресурсы. Проверка Free-плана и реального
потребления остаётся частью незавершённого развёртывания.

## Проверки без изменения рабочих задач

```sh
node --test external_watchdog/test/*.test.mjs
node external_watchdog/observe.mjs
```

Вторая команда только читает GitHub; `GITHUB_TOKEN` передаётся через окружение.
Локальные тесты проверяют наблюдение, восстановление на изолированных данных,
задержки, лимиты, очереди, неопределённые ответы и восстановление только записи.
Они не заменяют проверку Worker, Cron, привязки Durable Object и реального токена
в Cloudflare. При изменении параметров задача 7 остаётся заблокированной.

Состояние исходных мониторингов, Healthchecks, резервного GitHub dispatcher и
автоматизации ChatGPT не меняется. Поставленная пользователем на паузу
автоматизация ChatGPT не возобновляется этим проектом.
